# Coding Conventions

## Backend

- Target framework is `net10.0`; versions for EF Core, ASP.NET Core and Npgsql are pinned in `backend/Directory.Build.props`.
- Nullable reference types and implicit usings are enabled.
- EF tooling: `dotnet-ef` 10.x as a global tool.
- Keep Clean Architecture dependencies one-way: Domain -> none, Application -> Domain, Infrastructure -> Application/Domain, WebApi -> all for composition.
- Put business entities in `OrderMgmt.Domain`; do not place EF or HTTP concerns there.
- Application services own use-case logic and receive dependencies through interfaces in `Application/Common/Interfaces` or feature-specific `Interfaces` folders.
- Controllers should stay thin: authorize, validate route/body binding and delegate to application services.
- Return standard `ApiResponse` wrappers through `ApiControllerBase`.
- Use FluentValidation for request validation and Mapster registrations for DTO mapping where a feature needs mapping configuration.
- Protect endpoints with `[HasPermission(Permissions.<Module>.<Action>)]`; add new permission constants in `Domain/Constants/Permissions.cs` and seed them in `DbSeeder`.
- New persisted entities should have EF configuration under `Infrastructure/Persistence/Configurations`.
- Prefer soft delete for business entities that inherit `BaseEntity`. Use hard delete only for pure join entities such as role-permission assignments. The one documented exception is the demo branch delete (`DemoBranchService`, see Demo Branches And Background Jobs).
- Add EF migrations under `Infrastructure/Persistence/Migrations` using the WebApi project as startup project.

## Frontend

- Use React 18 + TypeScript + Vite.
- Keep route screens in `pages/`; keep module server-state access in `features/<module>`.
- A normal feature folder uses `api.ts`, `hooks.ts`, `types.ts`, optional `schema.ts` and optional `keys.ts`.
- Use TanStack Query hooks for API-backed state. Keep query keys centralized per feature when a module has more than trivial fetching.
- Use React Hook Form + Zod for forms that need validation.
- Use shadcn-style primitives from `components/ui` and layout components from `components/layout`.
- Sidebar navigation is declared only in `components/layout/nav-config.ts`. Add an item to the group of its type of work (`sales`, `inventory`, `cash`, `debt`, `reports`, `catalogs`, `system`) with `to`, `label`, an `icon` registry name whose drawing is not used by any other item or group, and `permission` / `anyPermission` / `role` for visibility; report items also carry `section` (Tổng hợp / Doanh thu / Kho / Quỹ / Công nợ) and sit next to the items of the same section. `nav-config.test.ts` asserts the order per role and icon uniqueness; update it with the item. Group colors are the `--nav-*` tokens in `index.css` (bare HSL channels, light and dark), used through the `bg-nav-<id>` classes; components never write color codes.
- The active sidebar item is the one whose `to` is the longest segment-boundary prefix of the path (`findActiveItem` in `components/layout/sidebar/nav-search.ts`); `/` matches only itself. A detail route needs no nav change as long as it lives under its list route.
- Sidebar UI state lives in `ui-store`: `sidebarGroupOpen` (only groups the user clicked; others use `defaultOpen`; shared by every user of the browser) and `pinnedNavPaths` (per user id, in pin order; pins of items the user cannot see are hidden, not removed).
- Gate pages with `ProtectedRoute permission="..."`; use permission-aware helpers for conditional UI.
- Keep API calls inside feature `api.ts` files and use `lib/api-client.ts` instead of raw Axios instances.
- Keep shared CSS tokens in `src/styles`; avoid one-off layout CSS when an existing token/helper fits.
- Icons: render `<AppIcon name=… />` from `@/components/icons`; never import `lucide-react` outside `src/components/icons/` (only `icon-registry.ts` maps drawings; ESLint and `no-direct-lucide-imports.test.ts` enforce it). Name icons by business meaning; add a missing name to the registry with a test line. Size by the `size` prop (8/12/14/16/18/20/24; stroke follows the size). Colour comes from the name's `tone` (`--icon-*` tokens: create cyan, edit blue, danger red, confirm emerald, info sky, export dark emerald, print indigo, accent violet, muted slate, warn amber); pass `tone="none"` on filled or coloured surfaces. Spinners: `ButtonLoader` inside buttons, `<AppIcon name="loading" />` elsewhere. Do not use characters (▲ ▼ ▾ ✕ ← →) as icons. In dense action bars keep button backgrounds restrained: the colour comes from the icon, not from a coloured button background, unless a screen explicitly needs stronger grouping.
- Back navigation: a child screen (a nested route such as `/settings/*`, or a drill-down target) shows `BackLink` (`components/layout/back-link.tsx`) before its h1. A fixed parent passes `to` directly. A drill-down parent navigates with `{ state: useFromHere() }`, and the child renders the link only when `useBackTarget()` returns a value. A page that is a drill-down child (or can be opened with `state.from`) rewrites its own query only through `useReplaceSearchParams` / `useSearchParamString` / `useSearchParamNumber` (`lib/use-search-param-state.ts`) or `useDashboardParams`, which all keep the history state; a bare `setSearchParams(…, { replace: true })` drops `state.from` (other pages may still use it). An effect that calls these setters must be guarded, because they change identity when the location state changes and the effect can loop. Do not use `navigate(-1)` for back buttons.
- In data tables, right-align numeric and currency columns in both headers and cells, and use `tabular-nums` for readable column scanning.

## Tests And Verification

- Backend integration tests live in `backend/tests/OrderMgmt.IntegrationTests`.
- Integration tests run against a local PostgreSQL through `TEST_DB_CONNECTION`, e.g. `Host=localhost;Port=5432;Database=qldonhang_integtest;Username=postgres;Password=1` (bash: `export TEST_DB_CONNECTION="..."`; PowerShell: `$env:TEST_DB_CONNECTION = "..."`). Without it, Testcontainers starts PostgreSQL in Docker.
- A worktree that runs backend tests while another session runs them elsewhere uses its own database name in `TEST_DB_CONNECTION` (for example `qldonhang_integtest_dash`): `PostgresFixture` drops and recreates `<base>_tpl` at the start of every run, so two runs on the same base name break each other.
- `PostgresFixture` migrates and seeds a template database `<base>_tpl` once per run; every `WebAppFactory` gets its own clone `<base>_<guid>`, dropped on dispose (clones a failing test did not dispose are dropped at the end of the run). The fixture never touches the base database named in `TEST_DB_CONNECTION`, refuses the dev databases `qldonhang_test` / `qldonhang`, and the factory overrides both `ConnectionStrings:Default` and `ConnectionStrings:DefaultConnection` (the app prefers `DefaultConnection`).
- New integration tests construct `new WebAppFactory(_pg)` (or inherit `QuotationTestBase`); derived factories take `PostgresFixture` (`: base(pg)`). The login rate limit is raised for tests via `RateLimiting:LoginPermitLimit`.
- A test double replaces a service through a derived host: `factory.WithWebHostBuilder(b => b.ConfigureTestServices(s => { s.RemoveAll<T>(); s.AddSingleton<T>(fake); }))` (`TinyPlans.WithService` / `WithServices` in `SampleData/`, `DashboardSignalTests`). The derived host shares the factory's database and starts its own hosted services, so the sample data worker's start-up recovery fails every demo branch still in `Running` there: start it (`_ = host.Services`) before making such a branch.
- Frontend tests use Vitest and Testing Library. Test files sit next to the behavior they cover, usually as `*.test.ts` or `*.test.tsx`.
- Run backend build/tests from `backend`; run frontend `npm run typecheck`, `npm run test` or `npm run build` from `frontend`.

## Local Development

- PostgreSQL and pgAdmin are provided by `docker-compose.yml`.
- Development backend configuration enables `Database:AutoMigrateAndSeed` and seeds `admin` / `Admin@123`.
- `appsettings.Development.json` currently points to `qldonhang_test` with `postgres` / `1`; when using the database from `docker-compose.yml`, override `ConnectionStrings__Default` to `qldonhang` with `qldh` / `qldh_dev_password`.
- Frontend dev server proxies `/api` to the backend through Vite config.

## Deployment Notes

- Backend and frontend each have a Dockerfile for Railway-style separate services.
- `VITE_API_BASE_URL` is a frontend build-time variable; changing it requires rebuilding the frontend image.
- For cross-domain auth, configure backend CORS and refresh cookie settings together.

## Inventory Patterns (Round 1)

- Type-dependent permissions (for example `stock_in.*` vs `stock_out.*`) are checked in the service when `[HasPermission]` cannot express them.
- Derived data (`InventoryLedgerEntry`, `InventoryCostPeriod`, `StockBalance`, `DocumentCounter`) does not inherit `BaseEntity`; it is hard-deleted and rewritten.
- Write use cases that touch stock run inside `ITransactionRunner` and call `IInventoryPostingService.AcquireLocksAsync` (shared branch gate, then product keys) before the first `SaveChangesAsync`. Read `InventorySettings` and `Branch.LockedUntil` after the locks, and re-check referenced products/warehouses there. `IInventoryLock` takes each key set in one statement; keep one advisory lock per product.
- Check-then-act guards on stock activity (product/warehouse delete, stock-field changes) run under the same locks as the postings they guard.
- A unique-index violation surfaces as 409 `DUPLICATE`; services still check uniqueness first to return a field-level 400.
- Every `DateTimeOffset` reaching EF is UTC (D27). VN-date rules are UTC ranges built with `VnTime.StartOfDay/StartOfNextDay`; never compare `.Date` of an instant.
- Never configure `HasDefaultValue(true)` on a non-nullable `bool` without `.HasSentinel(true)` (D28).
- New child entities (lines, activities, opening-stock rows) are added through their `DbSet.Add`: `BaseEntity` pre-assigns ids, so adding only through a navigation collection sends an UPDATE.
- Validation `details` keys are camelCase in both layers (`orderDiscount`, `lines[0].vatRate`); `ValidationDomainException` carries a Vietnamese summary message (its first detail by default).
- Pure calculators (`PricingQuantity`, `StockVoucherCalculator`, `PeriodicAverageCalculator`, `CostingPeriodCalendar`, `DocumentNumberFormatter`) live next to their feature and are unit-tested in `tests/OrderMgmt.IntegrationTests/Inventory/Unit` without a database.
- Frontend:
  - `npm run typecheck` runs `tsc -p tsconfig.app.json`.
  - Error handling uses `getApiError` / `formatApiErrorDetails` from `lib/api-client.ts`.
  - Dates go through `lib/vn-datetime.ts` (instants); never derive a local date with `toISOString().slice(0, 10)`. A DateOnly string (`yyyy-MM-dd`, for example a due date) is formatted with `formatDateOnly` (`lib/date-only.ts`), never through `new Date`.
  - Money in previews uses `roundAwayFromZero` (`lib/round.ts`); stock quantities use `formatStockQuantity`.
  - Branch-scoped queries (including `warehouseKeys`) live under the `['inventory']` root key. Change the working branch only through `useSwitchWorkingBranch`; pages are remounted per branch, so don't sync branch-derived state by hand.
  - Warehouse pickers use `selectableWarehouses` (active ones, plus the current inactive selection). Quantity inputs parse with `parseQuantityInput` (`lib/stock-quantity.ts`), money with `parseMoneyInput`.
  - Long synchronous calls (cost recalculation, costing settings) pass an explicit `timeout` and treat `isRequestTimeout` as "may still be running".
  - The service worker caches only allow-listed reference data that is the same for every signed-in user (`CACHEABLE_API_PREFIXES` in `lib/sw-routes.ts`); never add a branch-, user- or permission-scoped path there.
  - Service worker logic lives in pure modules next to `sw-routes.ts` (`lib/sw-push.ts`) and is unit-tested; `sw.ts` only wires listeners and is not type-checked. A push always shows a notification. A notification opens only a same-origin path (`resolveTargetUrl`), through the `NAVIGATE` message to the open window (`SwNavigateListener`).
  - Fixed or full-height mobile UI keeps clear of the iPhone notch and home indicator with `pt-safe` / `pb-safe` / `pl-safe` / `pr-safe` (`index.css`); `AppShell` already pads left, right and bottom, so content inside it needs nothing. An element with its own padding or offset uses `max(<value>, env(safe-area-inset-*))` instead (mobile search sheet, update popup, toast viewport). The toast viewport sits at the bottom center on every screen size and has `pointer-events-none`; only a toast takes clicks, so it never blocks the sticky action bar at the top of a form.
  - `vite.config.ts` imports `src/lib/pwa-icons.ts`; keep that file pure (no DOM, no `@/` imports). Branding icon URLs always go through `brandingIconUrl`, never a relative `/api/...` path in `index.html`. A new `VITE_*` variable needed in production also gets an `ARG`/`ENV` pair in `frontend/Dockerfile`.
  - The stock voucher form keeps every tab panel mounted (`forceMount`, hidden with `data-[state=inactive]:hidden`), so form fields keep their refs and ids. A field's tab comes from `tabOfField` (`pages/stock-vouchers/utils/voucher-tabs.ts`). Map any new header field there. The Thông tin khác tab is inline JSX in `stock-voucher-form-page.tsx`.
  - Grid keyboard rules live in pure functions in `pages/stock-vouchers/utils/line-navigation.ts`: the Enter path per pricing mode, previous/next stop, ↑/↓ target. Per-user grid settings live in `use-stock-grid-prefs.ts` (localStorage `qldh:stock-grid-prefs:{userId}:{In|Out}`, versioned, validated on read). A new grid input field must be added to `LINE_FOCUS_FIELDS` and, if the user may hide it, to `OPTIONAL_COLUMNS`. The grid, its cells and the column array all live in `components/stock-line-grid.tsx`; the settings popover is `components/stock-grid-settings-popover.tsx`.
    - On the stock and quotation line grids, **Số tấm**, **Dài**, **Rộng** and **Dày** follow the highest pricing mode of the lines. The rule lives in `lib/dimension-columns.ts`: `PRICING_MODES` in rank order (moved there from `line-navigation.ts`; import it from `@/lib/dimension-columns`), `normalizePricingMode` (a missing or unknown mode counts as `PerUnit`), `usesDimension` and `shownDimensions`. These four columns are not `OPTIONAL_COLUMNS` and have no per-user switch. A cell that its row does not use keeps its input id, is disabled, has an empty plain `value` (not `register`, so nothing is written back to the form) and shows "—" as its `placeholder`; the stored dimension is still saved and printed. On the stock grid a dimension error forces its column into view through `dimensionErrorFields` (`use-stock-grid-prefs.ts`), not `forcedColumns`. Columns that appear flash through `useAppearedKeys` (`lib/use-appeared-keys.ts`): class `col-appeared`, rules in `pages/quotations/components/line-items-grid.css`, header colour `--qldh-col-appeared-head-bg`, no animation under `prefers-reduced-motion`. Effects in a grid that read their rows through `form.getValues` in render (the flash hook, the scroll anchor) must not use a dependency list: React can discard a render but keep its deps (quick add commits from a timer), so they compare with the last committed value kept in a ref instead.
  - Enter never submits the stock voucher form. Save is Ctrl+S or the buttons.

## Cash & Debt Patterns (Round 2A)

- A warning the user may confirm is a `ConfirmationRequiredException` (`Code`, `Message`, `Details`), mapped to **422** like `NegativeStockException`. Codes: `DEBT_SETTLEMENTS_WILL_BE_REMOVED` (always confirmable), `CREDIT_LIMIT_WARNING` / `CREDIT_LIMIT_BLOCKED`, `NEGATIVE_FUND_WARNING` / `NEGATIVE_FUND_BLOCKED`. The request skips a warning with its flag: `confirmRemoveSettlements`, `acknowledgeCreditLimit`, `acknowledgeNegativeFund` (plus Round 1's `acknowledgeNegativeStock`). When several apply, the server reports them in this order: negative stock → settlements removal → credit limit → negative fund. `CanConfirm` is not serialized: a `_BLOCKED` code is never confirmable.
- Period lock checks in new code use `PeriodLockGuard.EnsureNotLocked` (`Application/Organization/Branches`), with instants or VN dates; settlements are checked on `EffectiveAt`. Round 1's private copies stay as they are.
- Every numbered document takes its code from `IDocumentCodeAllocator.NextAsync` (`peek: true` for `/defaults`). The cash series are `Receipt` (`PT`), `Payment` (`PC`), `FundTransfer` (`CQ`) and `DebtOffset` (`BT`), one counter per type × branch. A soft-deleted document's number is never reused: the `usedAmong` check reads soft-deleted rows too (`IgnoreQueryFilters()`), because a reset-policy change can restart the counter on codes of the old period.
- Document dates: once a branch has an opening date, a stock voucher, cash voucher, fund transfer or debt offset dated before it is rejected with `OpeningDateGuard.EnsureOnOrAfterAsync` (400 `voucherAt`), called after the shared branch gate. A due date is never before the document date (400 `dueDate`).
- Every cash/debt write runs inside `ITransactionRunner`, takes the shared branch gate (`IInventoryLock.AcquireBranchGateAsync(..., exclusive: false)`) and then `ICashDebtLock`. Global order: branch gate → product keys → partner keys `debt-partner:{branch:N}:{partner:N}` → fund keys `cash-fund:{fund:N}` → reason key (`cash-reason:{id:N}` / `stock-reason:{id:N}`, shared on voucher saves, exclusive on reason edit/delete) → counter row. Pass both the old and the new partner/fund ids on update. Read settings, `LockedUntil`, `OpeningDate`, credit limits, fund data and the reason **after** the locks (or re-check them there, as `StockVoucherService` does).
- Debt is written only through `IDebtLedgerService`: `PostAsync` on save (upserts entries in place by source and side) and `RemoveSourceAsync` on cancel/delete. Remove your own origin first with `RemoveOwnSettlementsAsync` (cash voucher edit with an allocation list: `AtVoucher`; stock voucher save: `Auto`; offset cancel/delete: `Offset`); that needs no confirmation and writes no activity. A draft with `Amount = 0` deletes the side as a shrink to 0 (its settlements ask `DEBT_SETTLEMENTS_WILL_BE_REMOVED`), unlike a missing draft (a removed side, 409). A settlement belongs to the document whose id is its `BatchId`, so settlements of these origins are added with the owning document's id as the batch; another document's settlement of the same origin (one cash voucher allocated against another) is not "own". Every other settlement then asks `DEBT_SETTLEMENTS_WILL_BE_REMOVED`, and changing the partner or side of a settled entry returns 409 `DEBT_HAS_SETTLEMENTS`. The `Auto` recompute needs no call in a write path: the ledger records both entries of every non-`Auto` settlement it removes in the scoped `SettlementChangeCollector`, and `AutoRecomputeHook` (an `IBeforeCommitHook`) runs `IAutoCashVoucherService.RecomputeAutoAsync` for them just before the commit. Only the outermost `ITransactionRunner.RunAsync` runs the hooks, so a ledger write under `RunSnapshotAsync` or in a transaction opened outside the runner skips the recompute. `RecomputeReopenedAsync` (period lock) is not a hook and is still called directly.
- The 422 `DEBT_SETTLEMENTS_WILL_BE_REMOVED` carries `error.token` (the settlement ids it lists: distinct, sorted, `N` format, comma-separated; every other error has `token: null`), built by `SettlementRemovalConfirmation`. The client resends it as `confirmedSettlements` with `confirmRemoveSettlements: true` (request DTOs; the opening debt DELETE takes it as a query parameter). The ledger accepts the confirmation when the token is absent (legacy accept-all) or covers every settlement the write would remove; otherwise it re-asks with a new 422 listing the current settlements. Merged 422s (stock voucher plus its automatic voucher, D-8) union their tokens, and `StockVoucherCashDebt.SyncDebtAsync` runs the stock step unconfirmed first so a stale token converges.
- Shared backend helpers; reuse them instead of adding copies:
  - `Application/Common/LikePattern` (`Escape`, `EscapeCharacter`): every `ILike` on an escaped pattern passes the escape character. The three cash document services use it; the copies in other services are still to be replaced.
  - `Application/CashDebt/Common/CashDocuments`: voucher date range, `NewActivity`, `ListActivitiesAsync`, `EnsureWorkingBranchAsync`, shared by the cash voucher, fund transfer and debt offset services.
  - `Application/Common/References/IReferenceUsage`: every "is used" check of partners, payment methods, branches and funds. Services keep their own messages and status codes; add a new "is used" check there, not in the service.
  - `IStockVoucherCashDebt` (`StockVoucherCashDebt`): the debt locks, debt sync (including D-8), drafts, and the credit and fund capture/check of a stock voucher save. `StockVoucherService` does not inject the lock, ledger, auto voucher service or guards itself.
  - `Application/Inventory/StockVouchers/Services/ProductCostPrices` (`RecomputeAsync`): the `Product.CostPrice` recompute from the latest active stock-in (D35), used by the stock voucher saves and the demo branch delete. It changes tracked products only, so the caller saves; a product with no stock-in left keeps its price.
- As-at debt reports (Round 2B): every report that shows the debt at a date reads the entries through `DebtPositionQuery` and never filters `PostedAt` itself. An entry counts at D when `PostedAt < StartOfNextDay(D)` or its source is `Opening`; a settlement counts at D only when both its entries do (B3). Each report keeps the identity with the balance report (B4: documents, aging and by-salesperson totals equal the closing balance) and the tests assert it for every partner and side. Empty results are zero-filled arrays, not empty ones (B12).
- Bucket boundaries (`buckets` parameter of `debt-aging` and `debt-overdue`): a comma-separated list of ascending positive integers, 1 to 6 of them, default `30,60,90`. Parse it only with `DebtAging.ParseBoundaries`: every boundary is capped at 36500 days (`DebtAging.MaxBoundaryDays`, keeps `boundary + 1` far from int overflow), and a blank value means the default. Invalid text is a 400 `buckets` validation error. Bucket *i* holds `b[i-1] < days <= b[i]`; aging starts at 0, overdue at 1; the DTO carries `{ from, to? }` and the client builds the labels (B5).
- Cash/debt integration tests live in `tests/OrderMgmt.IntegrationTests/CashDebt` (pure tests in `CashDebt/Unit`), inherit `CashDebtTestBase : InventoryTestBase`, use a fresh branch and partners, and end every ledger, settlement and debt-source scenario with `AssertCashDebtInvariantsAsync()`.
- Frontend:
  - Branch-scoped cash and debt queries live under the `['cash']` root key (`cashKeys.all` in `features/cash-common/keys.ts`). Stock voucher mutations invalidate `['inventory']` and `['cash']`; cash mutations invalidate `['cash']` and `['inventory']`.
  - The document forms (stock voucher, cash voucher, fund transfer, debt offset) and any new one use `hooks/useDocumentActions.ts`: it owns `busy`, the 422 chain (`toConfirmationRequest` / `withConfirmed` from `lib/confirm-required.ts`, which keeps the flags already confirmed, resends them all with the new one and also resends the settlement token as `confirmedSettlements`), the 409 reload and the `VALIDATION` / generic toasts. It also gives the focus back after an action or its 422 dialog: to the element the user was last on inside `main#main-content` (never a dialog control, a Radix focus guard, the app header or the sidebar), only when the focus is lost and that element is still usable, never after an action that started with nothing focused, and through `giveFocusBack` so a key still held down does not press it again. Focus helpers live in `lib/focus.ts` (`DIALOG_SELECTOR`, `PAGE_AREA_SELECTOR`, `isFocusLost`, `canTakeFocus`, `giveFocusBack`, `ignoreKeyRepeat` for the buttons of a dialog a key press may open); `components/ui/dialog.tsx` gives the focus back to what opened a dialog when it closes. The opening debt and fund opening balance dialogs call `toConfirmationRequest` / `withConfirmed` with `ConfirmRequiredDialog` directly. The client treats a code without a flag (`_BLOCKED`) as blocked.
  - Shared UI and helpers: `components/search-combobox` (behind `DebtPartnerPicker` and the ledger `PartnerPicker` only; `CashPartnerFilter` and `CustomerPicker` keep their own behaviour), `components/activity-history` (`ActivityHistory`, the activity list of every document), `components/money-cell` (`MoneyCell`, `CellError`), `lib/to-number.ts` (`toNumberOrZero`, `toOptionalNumber`) and `lib/money-input.ts` (money text parsing and formatting).
  - Each feature keeps its query keys in its own `keys.ts` (`credit-limits`, `opening-debts`, `cash-settings` included), never as inline arrays in hooks.
  - Never add a cash or debt path to `lib/sw-routes.ts`.

## TT133 Report Forms

- A form is a presentation of an existing report DTO and never queries the database itself. A new number goes into the report service first (as `ReasonName`, `DueDate` and `BranchCode` did), so the file always equals the screen; the tests assert each form's totals against its source report.
- One class per form in `Infrastructure/Excel/Tt133/` (`CashBookForm`, `DebtLedgerForm`, `DebtSummaryForm`, `DebtReconciliationForm`, `StockSummaryForm`, `StockDetailForm`, `StockCardForm`), called by `Tt133FormRenderer` (`ITt133FormRenderer`) and built with `Tt133FormBuilder`: header block (`WriteHeaderBlock`), title and parameter lines (`WriteTitle`), the two-tier table header with the symbol row (`WriteTableHeader`), rows and summary rows (`WriteRow`, `WriteSummaryRow`), the book footer (`WriteBookFooter`) and the page setup (`Finish`). The column table (`Tt133Column`) lives in the form class. Sheet names come from `Tt133FormBuilder.SheetName` and the period line from `Tt133FormBuilder.PeriodLine`.
- Exports go through `ITt133ExportService` (`Application/Tt133`). Each export loads its data (form context, targets, report DTOs) inside one `ITransactionRunner.RunSnapshotAsync`; rendering and the PDF conversion run after the snapshot is closed. `EnsureSheetCount` checks the number of sheets and `ToFileAsync` turns the workbook into the `ExportFile` (xlsx as is, or converted to PDF).
- Every export is a literal route `api/reports/{report}/export?format=xlsx|pdf` in `Tt133ExportController`, carrying the `[HasPermission]` of its source report: GET with the screen report's query for the single-document forms (`cash-book`, `debt-balance`, `debt-reconciliation`, `stock-summary`), POST with a JSON body for the multi-target forms (`debt-ledger`, `stock-card`, `stock-detail`), because a list of ids does not fit a URL. A permission `[HasPermission]` cannot express is checked in the export service (`stock-detail` needs `inventory.view_cost`).
- Errors: 422 `EXPORT_NO_TARGETS` and `EXPORT_TOO_MANY_SHEETS` are `UnprocessableException`s and are not confirmable (the client never resends them with a flag); 503 `PDF_EXPORT_FAILED` is a `ServiceUnavailableException`. Both classes are in `Domain/Common/DomainException.cs`.
- Limit: `Tt133Export:MaxSheets` (`Tt133ExportOptions`, default 300, bound in `WebApi/Program.cs`). It applies to explicit target lists and to "all with activity" alike; the request validators put no cap on the id lists.
- `ReportScope` and `ReportScopeGuard` (`Application/Common/ReportScope.cs`): `Company` drops the branch filter, skips demo branches and nothing else, needs `branches.access_all` (403 otherwise) and is offered only on the debt reports (`debt-balance`, `debt-ledger`, `debt-reconciliation`) and the stock summary, where it excludes a warehouse filter. A report service that takes a scope calls `ReportScopeGuard.EnsureAllowed` itself.
- A printed form never hides a filter. A search text is printed as a `Điều kiện lọc: mã hoặc tên chứa "…"` line (debt summary, S07). Company-scope ledger rows carry `BranchCode`, printed as `[code]` in front of "Diễn giải" on S12, the reconciliation record and the Sổ chi tiết công nợ screen, because document numbers repeat across branches.
- PDF conversion uses `ISpreadsheetPdfConverter` (`LibreOfficeSpreadsheetPdfConverter`, shared with the quotation exports and configured by the `QuotationExport` section). Tests replace it with a fake. The LibreOffice converter gives every conversion its own profile directory (`-env:UserInstallation`), because conversions that share the default profile fail when they run at the same time, and it kills its process tree when the wait is cancelled (timeout or request abort).
- Tests: pure tests of the builder and the forms in `tests/OrderMgmt.IntegrationTests/Tt133/Unit`, export tests in `Tt133/`; they read the workbook back with ClosedXML and find rows by label through `Tt133Sheet`, never by a fixed row number.
- Frontend:
  - A report page shows `Tt133ExportButton` (`components/tt133-export`) with one `Tt133ExportForm` entry per form (`code`, `report`, `params`, `fileBase`). ## Demo Branches And Background Jobs

- `IActingIdentity` is set only by background work, never inside an HTTP request. Set it once, right after creating a fresh scope (`IServiceScopeFactory.CreateAsyncScope()`), and run one unit of work in that scope; `Set` throws on a second call, because `AppDbContext` reads the user at `SaveChanges` for `CreatedBy`. `CurrentUser` and `CurrentBranch` answer from it, so services need no change to run in the background.
- A background job goes through a singleton in-memory queue (an unbounded `Channel` with a single reader, whose writer is never completed) and one `BackgroundService` in `WebApi/BackgroundJobs`, as `ISampleDataQueue` and `SampleDataHostedService` do. The service:
  - recovers interrupted work in an awaited `StartAsync` override before `base.StartAsync`, so recovery ends before the first request. Keep `HostOptions.ServicesStartConcurrently` at its default (`false`);
  - catches every exception: a failing job is logged as an Error and the next one runs; on shutdown it logs Information and stops;
  - runs each job in a fresh scope, inside a log scope with `UserId` and `CorrelationId`.
- The queue is in memory and the app runs as one instance. The state of a job lives on its database row, and the start-up recovery closes what a stopped process left.
- A job writes its own status only with a guarded `ExecuteUpdateAsync` whose `Where` requires the state the job expects (`IsDemo` and `Running` for the sample data). A row that is no longer in that state is left unchanged, with a Warning log. Once the host's stopping token is cancelled the job rethrows every exception, so the row stays for the recovery.
- Text a job stores for users (`SampleDataError`) never carries an internal exception message: known exceptions keep their message, the way `GlobalExceptionMiddleware` maps them, and anything else gets a generic Vietnamese message (`SampleDataRunner.FormatError`).
- Background work writes business data through the business services, after running the request through its `IValidator<T>`, never straight to their tables (its own status row aside). The one exception is the sample catalog (`SampleCatalogWriter`), because the create requests have no `IsSample`. It locks the sample product keys before it reads product state, inside a READ COMMITTED `ITransactionRunner.RunAsync`, never `RunSnapshotAsync`.
- A new company-wide query (a `ReportScope.Company` branch, the executive company scope, anything that adds up several branches) skips demo branches: `!_db.Branches.IgnoreQueryFilters().Any(b => b.Id == e.BranchId && b.IsDemo)` on rows, or `!b.IsDemo` on a branch list. Add a test next to `SampleData/CompanyScopeDemoTests` or `ExecutiveDemoExclusionTests`. A query of one named branch keeps demo branches.
- A new table with a `branch_id`, or a new foreign key into the branch's documents, funds, warehouses or the catalog (products, customers, customer addresses, product groups), needs its rows deleted in `DemoBranchService.DeleteAsync` (children before parents) or a reference check in its catalog cleanup. `DemoBranchDeleteTests` compares the foreign keys in `pg_constraint` with a known list and fails until the list is updated.
- The normal branch delete stays a soft delete and refuses demo branches (409 `DEMO_BRANCH_USE_DEMO_DELETE`).
- Tests: DB tests in `tests/OrderMgmt.IntegrationTests/SampleData` (`[Collection(nameof(PostgresCollection))]`, on `CashDebtTestBase`; the delete tests on `DemoBranchFixture`), pure tests in `SampleData/Unit`. Runner tests use small hand-made plans (`TinyPlans`) and `FakeSampleDataGenerator`; `RecordingSampleDataQueue` keeps the queue and leaves the worker idle.
- Frontend:
  - A list that shows a background job polls only while the job runs: `refetchInterval` from a pure helper (`branchesRefetchInterval` in `features/branches/sample-data.ts`) and `refetchIntervalInBackground: false`.
  - The demo branch delete cannot be undone, so its dialog asks the user to type the exact branch code, and the button waits for a preview that has loaded, without error, and is not refetching. Its query key is `branchKeys.demoDeletion(id)` in `features/branches/keys.ts`.

- Catalog dialog: Enter in its search box is ignored while the typed text is not yet searched or the shown rows are placeholder data, and a second select while a detail load runs is ignored.
- Reason match: `features/cash-common/reason-match.ts` mirrors `ValidatePartner` of both services (`requiredRole`, `partnerFitsReason`, `matchReasonForPartner`, `reasonMismatchMessage`, `reasonSwitchMessage`, `preferredPartnerRole`). Picking a partner switches the reason when it does not fit; changing the reason keeps the partner and shows a derived mismatch line; only a reason with partner type `None` clears the partner.
- Reason notice: one derivation, `reasonNoticeOf(partner, reason, switchNotice)` (`features/cash-common/reason-notice.ts`), and one component, `ReasonNoticeLine` (`reason-notice-line.tsx`), used by the cash header and the stock main fields: one `role="status"` paragraph under the reason select, where the field's own error wins; amber for the "reason changed" text, destructive for a mismatch. `useReasonSwitchNotice` (`use-reason-notice.ts`) keeps the text and flashes the select for 1.6 s. A reset from the server clears the notice (`applyServerVoucher` on the cash page, `resetTo` on the stock page).
- Cash voucher auto text: `useCashAutoText` is event-driven and never writes when a saved voucher opens or is reset (the Print button is disabled while the form is dirty, and the payment QR button follows the same rule once it is merged). The page sets baselines with `baseline(...)`; `initNew` fills a new voucher once the default reason is known and settles only on a baseline or on a user action whose auto text is not empty. The cash payload carries no `partnerTaxCode`: the server reads the catalog.
- F4 opens the quick add and the `+` button, which is Tab-reachable, does the same (F4 may need Fn on a laptop). Seed grants for new permissions reach only new databases: on a running database an admin enables them in the permission matrix.
- Product quick add: `ProductFormFields` (`features/products/components`) is the single product form, shared by the product page (`ProductFormPage`, `/products/new` and edit) and `ProductQuickAddDialog`, and it ignores a second submit while one runs. `useSaveProduct` owns the unit get-or-create step. `ProductTypeaheadCell` has an `allowQuickAdd` opt-in (the "Thêm mới hàng hóa" row and F4); the cell itself also requires `products.create`, so a form just sets the prop. A product created in the dialog is committed in `onCloseAutoFocus`, so the line is filled once the dialog has closed and the focus is back. `useDialogOpening` lives in `src/lib`.

## User Help

- Every app route (`frontend/src/app-routes.tsx`, leaf routes except `/login`, `/403`, `/404`, redirects and `*`) has exactly one help file in `frontend/src/features/help/content/<key>.md`, or is listed in `HELP_PENDING` (`features/help/help-pending.ts`), which only shrinks. `help-guard.test.ts` enforces it, plus valid files, existing `related` keys and `videos.json` steps. A new route goes into `app-routes.tsx`, never back into `App.tsx`.
- Key: the route without `/` and without `:param` segments, joined with `-`; `/` is `home`; a list/form pair gets `.list` / `.form`. One file may own several routes (a detail page with its parent).
- File format and writing rules (section 2 of `docs/brainstorms/261015-1001-user-help-guide/SUMMARY.md`, restated): frontmatter `key`, `title`, `routes`, `sources` (repo-relative globs, backend allowed), `related`, `updated`; sections `Dùng để` (at most 2 sentences), `Các bước` (3-7 one-line steps `N. {#id} text`, verbs first, stable ids), `Lưu ý`, `Phím tắt`; inline only `**label**` and `` `key` ``; no links.
- Every feature change ships its user guide in the same task and PR (rule in `AGENTS.md` "User Guide Rule"):
  - A new screen gets a new help file. `HELP_PENDING` is only for the routes that existed before round 1, and a new route never goes there.
  - A changed screen gets its help file updated to match the code, with `updated` set to today.
  - A changed screen still in `HELP_PENDING` gets its help file written and leaves the list.
  - A change to shared code updates every file `npm run help:stale` lists.
  - Only changes the user cannot see are exempt, and the PR says so.

  Run `npm run help:stale` before a release (it needs Node 22.18 or newer, which runs the TypeScript script by type stripping). Use the `help-content` skill to draft.
- UI: `HelpPanel` (rendered by `AppLayout`), `HelpButton` and `FirstVisitHint` (rendered by `AppHeader`), F1 through `useHelpShortcut`; state in `ui-store` (`helpOpen`, `helpHintSeen`, `helpHintsOff`). The content is one lazy chunk (`content-index.ts`); import it only through `load-help.ts`. F1 does nothing while a modal dialog is open (`DIALOG_SELECTOR` outside `POPPER_WRAPPER_SELECTOR`, `lib/focus.ts`); popovers never block it. From 768px to 1599px the panel lies over the page, so a press outside it (not on `[data-help-button]`, a dialog or a popper) closes it; from 1600px it is a column and stays open. Closing plays a 200ms shrink toward `[data-help-button]` (then a `help-ping` ring on the button), a slide down on phones, and nothing with reduced motion or from 1600px; `HelpPanel` keeps the panel mounted while it leaves, and each opening is a fresh panel.
- `videos.json` is written by the round-3 video tool, never by hand; a step's hash is `stepHash` from `parse-help.ts`.
